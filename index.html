IAM Identity Overview

Every AWS request is authenticated by an Identity and authorized by Policies

👤

IAM User

A permanent identity with long-term credentials (password / access keys). Represents a human or application.


Long-term credentials
🎭

IAM Role

A temporary identity with no credentials of its own. It is assumed by trusted entities for a session.


Short-term credentials
👥

IAM Group

A collection of IAM Users. Attach a policy once to the group; all members inherit the permissions.


Organizational tool
📜

IAM Policy

A JSON document that defines what actions on which resources are Allowed or Denyed.


Permission document
🔐

Trust Policy

A special policy attached to a Role that specifies who (principal) is allowed to assume it.


Role's door key
🏷

Permission Boundary

An advanced guard-rail that caps the maximum permissions an identity can have, even if a policy allows more.


Max permissions cap
💡 Golden Rule: By default AWS denies everything. An explicit Allow must exist, and an explicit Deny always wins — even over an Allow.

IAM Users

Permanent identities with long-term credentials attached to a single AWS account

What is an IAM User?

An IAM User is an entity you create in AWS to represent the person or application that uses it to interact with AWS. A user in AWS consists of a name and credentials.

Real Example: Your DevOps engineer Alice needs to deploy to EC2. You create an IAM user alice, attach an EC2 policy, and give her API access keys.

Credential Types

  • 🔑 Console password – login at console.aws.amazon.com
  • 🗝 Access Key ID + Secret Key – programmatic access (CLI / SDK)
  • 📲 MFA device – virtual (Authenticator app) or hardware token
  • 🖋 SSH keys – only for AWS CodeCommit
  • 🌐 HTTPS Git credentials – CodeCommit HTTPS

IAM User Limits & Best Practices

  • ⚠️ Max 5,000 IAM users per account
  • ✅ Always enable MFA for privileged users
  • ✅ Rotate access keys every 90 days
  • ✅ Follow least-privilege principle
  • ✅ Prefer IAM Roles for applications over users
  • ❌ Never share access keys between users
🎭

IAM Roles

Temporary identities that can be assumed by AWS services, users, or external entities

Why Roles instead of Users?

❌ IAM User for EC2 (BAD)

  • Hard-code access keys in app code or env vars
  • Keys can leak via logs, git history, memory dumps
  • Manual rotation across all instances
  • No automatic expiry

✅ IAM Role for EC2 (GOOD)

  • Instance Metadata Service (IMDS) automatically provides temp creds
  • Credentials auto-rotate every ~1 hour
  • No secrets stored anywhere
  • Audit via CloudTrail easily

Role Use Cases

  • 🖥 AWS Service Role – EC2, Lambda, ECS task needing access to S3/DynamoDB
  • 🔀 Cross-Account Role – Account A assuming a role in Account B
  • 🌐 Federated Role – External identity (Google SSO, SAML, OIDC) mapped to a role
  • 👷 Human Role – Developer temporarily elevating to Admin role with MFA

Role Anatomy

  • 📋 Trust Policy – defines who can assume this role (Principal)
  • 📜 Permission Policy – defines what the role can do
  • ⏱ Max Session Duration – 1–12 hours (default 1 hr)
  • 🏷 Session Tags – ABAC tags passed during AssumeRole
  • 🔒 Inline vs Managed – inline is embedded; managed is reusable

Step-by-Step Breakdown

  1. Caller invokes sts:AssumeRole

    The caller (IAM User, EC2 instance profile, or Lambda execution role) makes an API call to AWS STS with the ARN of the target role.

  2. STS validates the Trust Policy

    STS checks the role's Trust Policy: is the caller's ARN listed as an allowed Principal? Is the sts:AssumeRole action permitted?

  3. STS validates the caller's permissions

    The caller must also have a permission policy that allows sts:AssumeRole on the target role ARN (or *).

  4. STS issues temporary credentials

    On success STS returns: AccessKeyId, SecretAccessKey, SessionToken, and an Expiration timestamp (default 1 hr).

  5. Caller uses credentials for AWS API calls

    All subsequent requests are signed with the temporary credentials. CloudTrail records them as assumed-role sessions.

  6. Credentials automatically expire

    After expiry the credentials become invalid. The caller must call AssumeRole again to get fresh credentials — no manual rotation needed.

Trust Policy (Resource-Based Policy on a Role)

Specifies who is allowed to assume the role — the role's front door

Allows the EC2 service (ec2.amazonaws.com) to assume this role. Used for EC2 Instance Profiles.

// Trust Policy: allows EC2 service to assume this role { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Principal": { "Service": "ec2.amazonaws.com" ← the trusted entity }, "Action": "sts:AssumeRole" } ] }
Real World: Your web server on EC2 needs to read from S3. Attach a role with this trust policy + an S3 read permission policy. The EC2 SDK auto-fetches credentials via IMDS — no keys in code!

Allows IAM user/role in Account A (111122223333) to assume a role in Account B (444455556666).

// Account B's role trust policy — trusts Account A's admin user { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111122223333:user/alice" }, "Action": "sts:AssumeRole", "Condition": { "Bool": { "aws:MultiFactorAuthPresent": true ← MFA required } } } ] }
Real World: Your company has a centralised Security account. DevOps engineers in Account A switch to an AuditRole in each child account — one identity, many accounts, full audit trail.

Allows GitHub Actions CI/CD pipelines to assume a role without storing AWS credentials as GitHub secrets.

// OIDC Trust Policy for GitHub Actions { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" }, "Action": "sts:AssumeRoleWithWebIdentity", "Condition": { "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" }, "StringLike": { "token.actions.githubusercontent.com:sub": "repo:MyOrg/MyRepo:ref:refs/heads/main" ← scoped to 1 branch } } } ] }
Real World: Your Terraform CD pipeline on GitHub Actions deploys infrastructure to AWS. Zero long-lived secrets — GitHub presents an OIDC token, STS validates it and returns temp creds.

Allows any IAM user in the same account to assume the role only if MFA is present (break-glass admin role pattern).

// Trust Policy: any user in same account with MFA can assume { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::123456789012:root" ← entire account }, "Action": "sts:AssumeRole", "Condition": { "Bool": { "aws:MultiFactorAuthPresent": true }, "NumericLessThan": { "aws:MultiFactorAuthAge": 3600 ← MFA < 1hr old } } } ] }
Real World: You have a BreakGlassAdminRole. Normal developers have read-only access. When needed, they use their TOTP authenticator, assume the admin role for 1 hour, then it expires.

Principal Types

Type Example

Common Conditions

  • aws:MultiFactorAuthPresent: true — require MFA
  • aws:SourceIp: [...] — restrict by IP / VPC CIDR
  • sts:ExternalId: "secret" — cross-account confused deputy protection
  • aws:RequestedRegion: "us-east-1" — limit to a region
  • aws:PrincipalTag/env: "prod" — ABAC tag matching

Real-World Scenarios

How IAM Roles and AssumeRole power common AWS architectures

🔵 Lambda reads from DynamoDB

  1. Create IAM Role LambdaExecutionRole
  2. Trust Policy: Principal = lambda.amazonaws.com
  3. Attach permission policy: dynamodb:GetItem on table ARN
  4. Assign role to Lambda function
  5. Lambda SDK auto-assumes the role via STS at invocation
Zero credentials stored. Auto-rotated every hour.
// Trust Policy { "Principal": { "Service": "lambda.amazonaws.com" }, "Action": "sts:AssumeRole" } // Permission Policy { "Effect": "Allow", "Action": [ "dynamodb:GetItem", "dynamodb:Query" ], "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/Orders" }

🔀 CI/CD deploys to Prod account

  1. Tools Account (A): CodePipeline execution role
  2. Prod Account (B): Create DeployRole
  3. Prod's trust policy trusts Tools account role ARN
  4. Pipeline does AssumeRole into Prod's DeployRole
  5. Uses temp creds to deploy CloudFormation stack in Prod
  6. Creds expire — no lingering access

☸️ EKS Pod needs S3 access (IRSA)

IRSA (IAM Roles for Service Accounts) lets Kubernetes pods get AWS permissions without node-level credentials.

  1. Create OIDC provider for EKS cluster in IAM
  2. Create IAM Role with OIDC trust policy
  3. Annotate the Kubernetes ServiceAccount with the role ARN
  4. Pod automatically gets OIDC token via projected volume
  5. AWS SDK exchanges token for STS temp credentials
  6. Only that specific pod/SA gets access — not the whole node!
// IRSA Trust Policy { "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/oidc.eks.us-east-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE" }, "Action": "sts:AssumeRoleWithWebIdentity", "Condition": { "StringEquals": { "...:sub": "system:serviceaccount:default:my-app-sa" } } } // k8s ServiceAccount annotation annotations: eks.amazonaws.com/role-arn: "arn:aws:iam::123456789012:role/MyAppRole"

🔍 Auditor assumes read-only role

  1. Create SecurityAuditRole in each AWS account
  2. Attach AWS managed policy SecurityAudit
  3. Trust policy: trusts the auditor's home account IAM role
  4. Auditor assumes role in each account for max 1 hour
  5. All actions logged in CloudTrail under assumed-role session
  6. After 1hr session ends — zero residual access
This is the AWS Organizations "Audit Account" pattern. One identity, read access to 100+ accounts.
// Auditor's permission policy (in home account) { "Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::*:role/SecurityAuditRole" ↑ can assume this role in ANY account } // CLI switch to audit role in Account B $ aws sts assume-role \ --role-arn arn:aws:iam::444455556666:role/SecurityAuditRole \ --role-session-name audit-session-2024 \ --duration-seconds 3600 // Export returned credentials $ export AWS_ACCESS_KEY_ID=... $ export AWS_SECRET_ACCESS_KEY=... $ export AWS_SESSION_TOKEN=...

IAM Policy Evaluation Logic

How AWS decides Allow or Deny for every API call — in order

Evaluation Order

  1. Explicit Deny in any policy → DENY immediately
  2. AWS Organizations SCPs (if present) must Allow
  3. Resource-based policy Allow → can grant cross-account
  4. Identity-based policy (user/role/group) Allow
  5. IAM Permission Boundaries must Allow
  6. Session Policies (passed at AssumeRole time) must Allow
  7. If no explicit Allow found → DENY (implicit)
Key Insight: A Deny anywhere in the chain overrides every Allow. To be granted access, all applicable policy layers must permit the action.

CLI & SDK Examples

Real commands you'll use every day working with IAM and AssumeRole

Create IAM Role (CLI)

# 1. Create the role with a trust policy file aws iam create-role \ --role-name MyAppRole \ --assume-role-policy-document file://trust.json # 2. Attach a managed permission policy aws iam attach-role-policy \ --role-name MyAppRole \ --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess # 3. Verify the role aws iam get-role --role-name MyAppRole

AssumeRole + Use Credentials

# Assume role and get temp credentials CREDS=$(aws sts assume-role \ --role-arn arn:aws:iam::111122223333:role/DeployRole \ --role-session-name deploy-$(date +%s) \ --query 'Credentials' \ --output json) # Export the temp credentials export AWS_ACCESS_KEY_ID=$(echo $CREDS | jq -r .AccessKeyId) export AWS_SECRET_ACCESS_KEY=$(echo $CREDS | jq -r .SecretAccessKey) export AWS_SESSION_TOKEN=$(echo $CREDS | jq -r .SessionToken) # Verify who you are now aws sts get-caller-identity

Python boto3 – AssumeRole

import boto3 # Create an STS client sts = boto3.client('sts') # Assume the role response = sts.assume_role( RoleArn='arn:aws:iam::111122223333:role/MyRole', RoleSessionName='my-session', DurationSeconds=3600 ) creds = response['Credentials'] # Use the temp credentials s3 = boto3.client( 's3', aws_access_key_id=creds['AccessKeyId'], aws_secret_access_key=creds['SecretAccessKey'], aws_session_token=creds['SessionToken'] ) s3.list_buckets()

Terraform – IAM Role & Trust Policy

# IAM Role resource resource "aws_iam_role" "lambda_exec" { name = "lambda-execution-role" assume_role_policy = jsonencode({ Version = "2012-10-17" Statement = [{ Effect = "Allow" Principal = { Service = "lambda.amazonaws.com" } Action = "sts:AssumeRole" }] }) } # Attach policy to role resource "aws_iam_role_policy_attachment" "s3_read" { role = aws_iam_role.lambda_exec.name policy_arn = "arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess" }

IAM Cheat Sheet

Quick reference for the most important concepts

Key ARN Formats

# IAM User arn:aws:iam::123456789012:user/alice # IAM Role arn:aws:iam::123456789012:role/MyRole # Assumed Role Session arn:aws:sts::123456789012:assumed-role/MyRole/session-name # IAM Policy arn:aws:iam::123456789012:policy/MyPolicy # AWS Managed Policy arn:aws:iam::aws:policy/ReadOnlyAccess

Most Used IAM Actions

sts:AssumeRole Get temp creds for a role
sts:GetCallerIdentity Who am I? (account/user/role)
iam:PassRole Assign a role to a service
iam:CreateRole Create a new IAM role
iam:AttachRolePolicy Attach managed policy to role
iam:SimulatePrincipalPolicy Test if a principal can do X

Security Best Practices

  • 🔒 Lock down root account — enable MFA, never use daily
  • 🎭 Use IAM Roles everywhere (services, humans, CI/CD)
  • 🏷 Use ABAC (Attribute-Based AC) for dynamic permissions
  • 🔭 Enable AWS CloudTrail + CloudWatch for audit logs
  • 📊 Use IAM Access Analyzer to find over-permissive policies
  • 🛡 Apply Permission Boundaries on delegated admin roles
  • 🔑 Enable SCP at the Org level as a safety net
  • ⏱ Use short session durations for sensitive operations
